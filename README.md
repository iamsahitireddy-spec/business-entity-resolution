# Business Entity Resolution Challenge

A machine learning solution for resolving noisy business records across multiple independent data sources.

---

## 📌 Project Overview

This repository contains the team submission codebase for the **Business Entity Resolution Challenge**. The core goal of this project is to match business records across three independent data sources without relying on common unique business identifiers.

### Data Sources
- **Source 1 (`S1-`)**: Deduplicated reference business entities.
- **Source 2 (`S2-`)**: Noisy business records.
- **Source 3 (`S3-`)**: Noisy business records.

### The Entity Resolution Problem
For **every** business record in **Source 1**, our pipeline must determine which records from **Source 2** and/or **Source 3** represent the same real-world business entity.

Key properties of the data matching problem:
- **Variable Match Cardinality**: A Source 1 entity can have **zero matches** (singleton), **one match**, or **multiple matches** across Source 2 and Source 3.
- **Record Noise**: Records exhibit inconsistent business names, missing/formatted address components, punctuation differences, legal suffix variations (e.g., *Corp* vs. *Corporation*, *Pvt* vs. *Private*, *Ltd* vs. *Limited*), typos, word-order permutations, transliteration, and landmark-based addresses.
- **Open-Set Country Field**: Training data covers US and India; test data includes additional countries (e.g., France). Country is treated as an open-set string field without hard-coded country logic.

## 🏗️ High-Level Pipeline Architecture

The solution follows a standard modular entity-resolution architecture:

```
┌─────────────────┐
│   Data Loader   │ ──► Reads TSV data files (S1, S2, S3, Ground Truth)
└────────┬────────┘
         │
┌────────▼────────┐
│  Preprocessing  │ ──► Business name & address normalization
└────────┬────────┘
         │
┌────────▼────────┐
│ Candidate Gen.  │ ──► Blocking stage to prune comparison space
│   (Blocking)    │     Outputs: candidate_pairs.tsv
└────────┬────────┘
         │
┌────────▼────────┐
│  Feature Eng.   │ ──► Pairwise string, token, TF-IDF & address features
└────────┬────────┘
         │
┌────────▼────────┐
│ Matching Model  │ ──► ML pairwise scoring & threshold optimization
└────────┬────────┘
         │
┌────────▼────────┐
│ Inference & Out │ ──► Decision thresholding & formatting
│                 │     Outputs: matching_results.tsv
└─────────────────┘
```

## ⚠️ Competition Rules & Guidelines

1. **Strict Prohibition of External Data**:
   - **DO NOT** use external business databases, government business registries, geocoding APIs, commercial entity-resolution APIs, internet searches, or external data augmentation.
   - All resolution must strictly rely on the provided dataset and permitted local models/libraries.

2. **Data File Format**:
   - All dataset files are Tab-Separated Values (TSV).
   - All files must be read using tab separation:
     ```python
     import pandas as pd
     df = pd.read_csv(filepath, sep="\t")
     ```
   - **Never** assume comma-separated CSV format.

3. **Evaluation Metric**:
   - The competition evaluates using **Macro-averaged F0.5** score:
     $$F_{0.5} = \frac{1.25 \times \text{Precision} \times \text{Recall}}{0.25 \times \text{Precision} + \text{Recall}}$$
   - F0.5 heavily penalizes false positives (false merges).
   - Correctly identifying singletons (predicting an empty match list for a true singleton) yields a perfect 1.0 for that entity, whereas predicting a false match yields 0.

```
├── output/
```

Submission validation command:
```bash
python3 utils/validate_submission.py \
  --matching output/matching_results.tsv \
  --candidate output/candidate_pairs.tsv \
  --test-dir dataset/test
```
